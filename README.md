本專案以單檔 Python 程式設計作業為對象。教師提供題目、規準、測試及學生程式後，系統先以 Podman 在隔離環境中執行正式測試，再由本機 Llama 3.2 3B 依測試摘要選擇檢查失敗案例、執行教師補測、提出評分或送交複核。每筆批改均保存工具結果、模型決策、簡短理由及最終狀態。客觀功能分與模型建議分項分開保存。

## 批改單位與測試資料

**一次執行 `grade.py` 會選定一道題目、批改一份學生程式，並產生一份報告。** 例如，`01_scores/S03` 代表「成績統計」的第 3 份學生解答。系統會把該題的 10 組正式輸入逐一交給同一份程式執行。因此，報告中的「通過 9/10」表示這份解答通過九個測試案例。

測試資料取自三道自製的 Python 入門題。每題有 15 種解答，涵蓋正確寫法與常見錯誤。每種解答各有一份繁中版與英文版，合計 **45 種解答、90 個作業檔**。同題、同編號的兩個語言版本保留相同邏輯與測試，便於觀察語言改變時，模型的理由與建議分數是否一致。

| 題目 | 學生程式要完成什麼 | 選用這題要觀察什麼 |
|---|---|---|
| `01_scores` 成績統計 | 印出筆數、平均與及格人數 | 一般成績能算對時，Agent 能否找出空資料除以零或漏算 60 分等邊界錯誤。 |
| `02_parking` 停車費試算 | 依停車分鐘數計算累進費用 | 能否區分跨級距算錯金額，以及迴圈未結束導致的逾時。 |
| `03_words` 最高詞頻 | 忽略大小寫計數，同票時取字母順序最前的單字 | 能否利用實際與預期輸出的差異，區分分詞、計數與同票排序問題。 |

以成績統計為例，下列檔案在同一筆批改中扮演不同角色：

| 資料 | 誰在什麼時候使用 | 例子 |
|---|---|---|
| 學生樣本 `submissions/S03.py` | 教師選定的受批改程式 | 這份解答處理一般成績正常，但在空輸入時計算平均會除以零。 |
| 正式測試 `official_tests.json` | 執行工具逐一讀取輸入與預期輸出；同題所有解答共用十案，每案 6 分 | T02 給空輸入，要求輸出 `0 0.00 0`；S03 在此案發生例外，功能分為 54/60。 |
| 診斷補測 `diagnostic_tests.json` | 每題提供三案，供 Agent 在需要額外證據時選用；補測結果只用於解釋 | D01 只含空白字元，可檢查這份程式遇到「讀不到任何分數」時的行為。 |
| 教師驗收資料 `teacher_only/` | 批改結束後，由 `check_evidence.py` 依樣本編號核對紀錄 | 可核對 S03 的 9/10 與除零例外。正式批改時，Agent 取得的是實際測試結果。 |

### 使用限制及原因

| 目前範圍 | 設計原因與使用影響 |
|---|---|
| 一次一份，可重複執行 | 作業二優先驗證單一學生從測試、補查到評分的完整流程。每次產出獨立的 `runs/*.json`，方便教師追溯各步證據。整班名單、批次進度與彙整成績單列於後續階段。 |
| 題目限上述三題，採固定規準 | 每題已有可核對的輸入輸出與規準。外部學生檔可用 `--file` 批改，但須回答 `--task` 選定的題目。新增題目或改變配分需同步調整題目選項、測試及計分程式。 |
| 學生程式為 UTF-8 單一 `.py`，最多 16 KiB，使用 Python 標準函式庫與標準輸入／輸出 | 執行器每案只接收一份原始碼與一筆輸入。此範圍符合三道入門題，也讓每份作業能在相同環境中精確比較輸出。需要多個檔案、額外套件、網路或互動介面的作業超出本階段範圍。 |
| 單案限時 2 秒，輸出達 16 KiB 即記為超限；預設最多補查兩次 | 單案限制可停止無窮迴圈或大量輸出；補查上限則控制模型反覆查詢。若正式案例失敗且額度用盡時仍未檢視失敗證據，系統保留客觀分數並送教師複核。 |
| 主觀分數屬教師確認前的建議 | 功能分可用正式案例重算。邏輯、規格與可讀性分數涉及模型判斷；成績統計 S03 的中英文實測皆得功能分 54/60，但建議總分分別為繁中 73、英文 85。 |


## 一、首次重現

驗證環境為 Apple Silicon macOS、Podman 6.0.2、Ollama 0.40.16、主機 Python 3.12 與容器 Python 3.12.16。主機端僅使用 Python 標準函式庫。批改與學生測試使用同一專案映像的兩個獨立執行環境。受測基底為 `docker.io/library/python:3.12-slim`，本次本機映像摘要為 `sha256:c61cffc3bacb94ed026ff8b45d5114b7693dd0420baca0a1ace0e3d0ce9035fd`。

1. 取得完整專案後，在含有本 README 與 `Containerfile` 的目錄開啟終端機。主機需有 Python 3.10 以上、Podman 與正在執行的 Ollama。macOS 首次使用 Podman 時，以 `podman machine list` 確認機器是否存在。尚未建立時執行 `podman machine init`，已建立且停止時執行 `podman machine start`。
2. 下載模型與 Python 基底，建置專案映像：

   ```sh
   ollama pull llama3.2:3b
   podman pull docker.io/library/python:3.12-slim
   podman build --pull=never -t localhost/grading-agent:hw2 .
   ```

   建置時，Podman 依照 `Containerfile` 把 `app/agent.py` 與 `app/worker.py` 放入映像。後續執行 `grade.py` 時，主機會使用此映像啟動應用容器及各案例的測試容器。

3. 檢查模型服務。第一行從 Mac 查詢，第二行從應用容器查詢。兩者的模型清單均應包含 `llama3.2:3b`。

   ```sh
   curl -fsS http://localhost:11434/api/tags
   podman run --rm localhost/grading-agent:hw2 python -c 'from urllib.request import urlopen; print(urlopen("http://host.containers.internal:11434/api/tags", timeout=5).read().decode())'
   ```

4. 執行第一筆批改：

   ```sh
   python3 grade.py --lang en --task 01_scores --sample S03
   ```

   **可核對的預期結果**為正式案例通過 9/10、功能分 54/60。T02 提供空輸入，學生程式在第 6 行計算平均時觸發 `ZeroDivisionError`。本次展示紀錄中，Agent 呼叫 `inspect_case(T02)` 後提出評分。終端機最後一行會列出當次完整 JSON 檔的位置。模型分項及總分屬評分建議，實測版本與模型設定見下方。

## 二、各程式的用途與使用方式

以下指令均從專案根目錄執行。**批改一份作業**的操作入口是 `grade.py`。**驗收**有兩個入口：`check_evidence.py` 核對已保存的成績紀錄，`test_tools.py` 重新執行容器測試。`app/` 下的兩支程式由啟動器自動執行。

### `grade.py`｜批改一份學生作業

執行時先以 `--lang` 和 `--task` 選定題目、規準與測試，再以 `--sample` 或 `--file` 指定學生程式。以英文成績統計 S03 為例，啟動器會從 `grading_lab/en/01_scores/` 讀取 `assignment.md`、`rubric.json`、`official_tests.json`、`diagnostic_tests.json`，並批改 `submissions/S03.py`。每次處理一份作業，批改前需啟動 Podman、建置專案映像並開啟 Ollama。

| 操作目的 | 從專案根目錄執行 |
|---|---|
| 批改預設的英文成績統計 S03 | `python3 grade.py` |
| 批改英文停車費 S13，觀察逾時案例 | `python3 grade.py --task 02_parking --sample S13` |
| 批改繁中單字統計 S02 | `python3 grade.py --lang zh-Hant --task 03_words --sample S02` |
| 用檔案路徑指定程式 | `python3 grade.py --task 01_scores --file "grading_lab/en/01_scores/submissions/S03.py"` |
| 列出所有參數與選項 | `python3 grade.py --help` |

以其他學生程式取代範例時，將 `--file` 後的路徑換成該檔案，並以 `--task` 選擇它要回答的題目。檔案須為 UTF-8 編碼的單一 `.py`，大小上限 16 KiB。使用內附樣本時，三題均可指定 `S01` 至 `S15`。模型位置及補查上限的參數見第五節。

**依序批改同題的 15 份樣本。** 在專案根目錄執行以下指令，可讓終端機逐一啟動單份批改。每個學生檔都會有自己的執行編號與報告。

```sh
for submission in grading_lab/en/01_scores/submissions/S*.py; do
  python3 grade.py --lang en --task 01_scores --file "$submission"
done
```

**讀取結果。** 終端機先印出最終評分或複核原因，最後一行 `Trace: runs/…json` 指向本次完整報告。以隨作業繳交的 [S03 實測報告](evidence/01-score-empty-en.json) 為例：

| 要確認的內容 | 報告欄位 | S03 的實測結果 |
|---|---|---|
| 最終狀態與分數 | `result.status`、`result.functional_points`、`result.total` | `proposed`；功能分 54/60，本次建議總分 85/100。 |
| 哪個輸入使程式失敗 | `test_results` 中 `case_id` 為 `T02` 的紀錄 | 輸入為空字串，`status` 為 `runtime_error`，`detail` 記錄除零例外。 |
| Agent 如何找到原因 | 依序閱讀 `trace` 中的 `action`、`tool_call` 與 `observation` | 正式測試後，模型選擇 `inspect_T02`；工具回傳 traceback，之後模型選擇 `grade`。 |
| 評語引用哪一行 | `result.cited_source`、`result.source_basis` | 第 6 行 `mean = sum(scores) / count`，行號取自 traceback。 |

### `app/agent.py`｜決定何時補查、評分或複核

`grade.py` 啟動應用容器後，會將題目、規準、學生原始碼、可用補測編號及模型設定送入 `agent.py`。它先要求執行正式測試，再把測試摘要送給 Ollama。模型每次選擇一個動作，例如檢視 T02；`agent.py` 向主機要求工具結果，取得觀察後再決定下一步。完成時會驗證分項分數與理由，將結果傳回 `grade.py` 寫入報告。

**觀察方式**：執行上表的預設批改指令，開啟本次報告的 `trace`。`by: workflow` 表示固定流程的決策，`by: model` 表示模型的選擇，`reason` 保留當步理由。

### `app/worker.py`｜隔離執行一個測試案例

每當正式測試或補測需要執行學生程式，`grade.py` 會為該案另開一個無網路容器，將學生原始碼與單筆標準輸入交給 `worker.py`。它收集實際輸出、例外或逾時狀態後交回主機。程式正常結束時，主機再比對實際與預期輸出，判定 `pass` 或 `wrong_output`。

**觀察方式**：使用 `python3 grade.py --task 02_parking --sample S13`，在報告的 `test_results` 尋找 `T01`。本案例輸入 61 分鐘，該份學生程式在時限內未結束，紀錄的狀態為 `timeout`。單獨驗證這個執行環境時，可使用下方的工具整合測試。

### `check_evidence.py`｜用教師答案核對已存的報告

此程式只需要主機 Python。它讀取報告中的題目、語言與樣本檔名，到 `grading_lab/teacher_only/` 找到對應答案，逐案核對狀態、可比對的輸出、通過數與功能分。若已提出總分，還會檢查分項加總與引用的案例編號。

```sh
# 核對隨作業繳交的七份報告
python3 check_evidence.py

# 只核對其中一份
python3 check_evidence.py evidence/01-score-empty-en.json
```

第二行指令的預期輸出為 `01-score-empty-en.json: 10 official cases, 54/60, proposed`。要核對新產生的內附樣本報告，可把檔名換成終端機 `Trace:` 顯示的路徑。此核對適用於具有教師答案、且已跑完十個正式案例的樣本；模型評語的正確性仍需依原始證據判讀。

### `test_tools.py`｜重跑隔離執行與補測工具

此程式透過 Podman 實際建立測試容器，可在模型服務關閉時執行。兩個測試方法分別檢查五種學生程式結果（通過、輸出不符、執行錯誤、語法錯誤及逾時），以及教師補測 D01 的執行結果、重複或未知補測編號的處理。

```sh
python3 -m unittest -v test_tools
```

成功時兩個測試方法皆顯示 `ok`，結尾顯示 `Ran 2 tests` 與 `OK`。此指令用於驗證工具行為；學生的批改報告由 `grade.py` 產生。

### 資料集中的 Python 檔案

每個題目資料夾的 `reference.py` 是教師參考解；`submissions/S01.py` 至 `S15.py` 是受批改的學生樣本。兩者都從標準輸入讀取題目資料，將答案寫到標準輸出。例如，在專案根目錄執行下列指令，可用參考解確認英文成績統計題的輸出格式：

```sh
printf '80 70 90\n' | python3 grading_lab/en/01_scores/reference.py
```

預期輸出為 `3 80.00 3`，依序代表成績筆數、平均分數與及格筆數。需要核對學生樣本時，以 `grade.py` 啟動隔離批改。

## 四、容器與工具

```text
主機端 grade.py 讀取單份作業、規準和測試
  ├─ 應用容器：決策、狀態、規準評分、證據檢查
  │    └─ 透過 /api/chat 呼叫主機 Ollama
  ├─ 工具請求經固定的訊息格式交給主機啟動器
  │    └─ 每個執行案例建立獨立的學生測試容器
  └─ 匯整最終狀態、觀察值及決策追蹤至 runs/
```

應用容器沒有 Podman 管理 socket 和主機檔案掛載。主機端只轉送三種已定義的工具請求。模型選擇工具與教師定義的案例 ID，學生測試容器只收到單份原始碼與該案輸入。預期輸出、模型服務及教師答案均留在學生執行環境之外。

| 工具 | 用途與輸入 | 輸出 | 錯誤處理 |
|---|---|---|---|
| `run_official` | 固定流程啟動；使用當次學生程式與題目共用的 10 個案例 | 每案輸入、預期及實際輸出或錯誤，供計分及後續檢查 | 學生錯誤列入該案結果；Podman 或工具服務失敗時整筆轉為待處理。 |
| `inspect_case` | LLM 指定一個已執行的失敗正式案例 ID | 讀取該案已保存的原始證據；有 Python 例外時包含 traceback | 僅接受當次可查 ID。證據不足或達上限時可送教師複核。 |
| `run_probe` | LLM 指定一個允許的教師補測 ID | 重新建立測試容器，回傳補測結果 | 拒絕未知及重複補測；補測不計入功能分。 |

學生測試採無網路、唯讀根檔案系統、每容器最多 1 CPU、128 MiB 記憶體及 32 個程序。測試主管程序建立暫存檔並以 UID/GID 65534 執行學生程式，單案限時 2 秒，標準輸出或錯誤輸出達 16 KiB 即記錄超限。容器啟動器另設上限以處理基礎設施異常。驗證範圍為自製教學樣本。

## 五、評分、狀態與操作

功能分為正式通過數 × 6；算法與邊界處理合計 25 分、規格 10 分、可讀性 5 分。總分由程式計算。若合法輸入造成執行中斷，該份作業的邊界處理與規格無法取得該項滿分。每份作業使用相同限制。遇正式測試失敗時，至少須實際檢視一個失敗案才能提出分數；模型也可直接選擇複核。預設最多補查兩次。

| 最終狀態 | 意義 |
|---|---|
| `proposed` | 結構與分數範圍通過檢查，附上實測事實、分項與建議總分，供教師確認。例外行號優先取自 traceback，其他程式位置標示為模型引用。 |
| `needs_review` | 證據不足、達補查上限、模型選擇複核，或模型回覆未通過格式及基本說明檢查。保留已得功能分，省略總分。 |
| `pending` | 模型或工具連線、容器等系統問題。保留已完成測試，省略總分。排除問題後以原指令重跑，產生獨立的新紀錄。此狀態的 CLI 結束碼為 2。 |

```sh
# 驗證複核上限及模型服務不可用的處理
python3 grade.py --sample S03 --max-checks 0
python3 grade.py --sample S03 --ollama-url http://127.0.0.1:1
```

`--lang` 支援 `en` 及 `zh-Hant`；`--max-checks` 可設 0 至 4。模型名稱、位置可用 `--model`、`--ollama-url` 或環境變數 `GRADER_MODEL`、`GRADER_OLLAMA_URL` 指定。模型溫度固定為 0、seed 為 42。正式成績以教師確認為準。預期輸出按換行正規化後精確比對，雙方各可忽略一個結尾換行。
